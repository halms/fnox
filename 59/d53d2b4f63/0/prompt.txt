You're right about the mechanism, and fnox is where it comes from.

~/dev/config/dotfiles/config/shell/zsh_tools:25 does source <(fnox activate zsh), which installs this precmd/chpwd hook:

_fnox_hook() {
  trap -- '' SIGINT
  eval "$(fnox hook-env -s zsh)"
  trap - SIGINT
}

So every prompt, zsh evaluates whatever fnox hook-env writes to stdout. Your AWS session was expired, fnox offered the login, and aws sso login's stdout was inherited by fnox's stdout instead of going to the tty. Those lines landed inside the command substitution and got eval'd:

zsh: command not found: Attempting
(eval):4: no such file or directory: https://kpler-sso.awsapps.com/start/#/device
zsh: command not found: KKDS-PWNM

(eval):4: is line 4 of the captured text – the URL line. The login itself worked ("Successfully logged into Start URL"), and fnox: +9 DATABASE_URL, … shows the retry resolved. Only the leftover text was executed.

This is a fnox bug: hook-env must keep everything except shell code off stdout, including the stdout of any child it spawns. Worth an issue against jdx/fnox.

Workaround: keep the browser flow out of the hook by making it cached-only, so an expired session just fails quietly and you run mise run aws:login (or aws sso login) yourself.

# fnox
if hascmd fnox && [[ -z "${IN_NIX_SHELL}" ]] ; then
    source <(fnox activate zsh)
    # hook-env output is eval'd, so an interactive login would leak its stdout into the shell.
    _fnox_hook() {
        trap -- '' SIGINT
        eval "$(FNOX_NON_INTERACTIVE=1 command fnox hook-env -s zsh)"
        trap - SIGINT
    }
fi
